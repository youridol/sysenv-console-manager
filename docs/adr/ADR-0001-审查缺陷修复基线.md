# ADR-0001：SECM 全量审查缺陷修复基线

- 状态：已接受
- 日期：2026-09-24
- 决策者：SECM 维护者
- 相关范围：`src/`、`src-tauri/src/`、`datasource/`、`sidecar-lhm/`、`scripts/`
- 依据：2026-09-24 全量全链路严格审查报告（2 阻断 / 9 严重 / 30 一般 / 18 建议）

## 背景

对全仓执行一次「入口枚举 → 三类流追踪 → 逐层排查 → 交叉验证」的审查，结论为：
构建与测试本体全部通过（`npm run build`、`npm run lint`、`cargo check --all-targets`、
datasource 47 项单测、src-tauri 240 项单测、8 个契约集成测试目标），但存在两类系统性问题：

1. **门禁失真**：指定的测试运行器在测试失败时仍以 0 退出，提交前钩子未生效，
   便携包对空驱动目录放行。这些使「构建通过」不再是可信信号。
2. **契约断层**：跨进程/跨线程/跨语言边界处，写入方与读取方对同一份状态的所有权
   假设不一致（取消注册表、sidecar tier-2 可变状态、IPC 参数名、日志 scope 真源）。

本 ADR 记录针对全部审查结论所采纳的修复决策。缺陷的完整证据（文件:行、命令、原始输出）
见审查报告；本记录只承载**决策与理由**，不重复证据。

## 决策

### D1 取消由命令侧显式注册（阻断）

- 问题：`cancel_flag` 生产调用点为 0，`cancel_command` 只置位已存在的键，`is_cancelled` 恒 false。
- 决策：五条流式命令（`ping_stream`/`traceroute_stream`/`nslookup_stream`/`detect_nat_type_stream`/`iperf3_stream`）
  在进入执行体前调用 `crate::cancel::cancel_flag(&cmd_id)`；`clear_cancel` 保持出口调用，形成入口注册、出口清理的严格配对。
  `cancel_command` 保持「仅置位已存在项」语义。
- 理由：所有权清晰，标志生命周期由命令界定；不使用惰性创建，避免迟到取消留下永不清理的孤儿条目。

### D2 测试运行器 fast-fail（阻断）

- 问题：`scripts/test-lib.sh` 只有 `set -e`，`cargo test ... | tail -40` 的退出码取管道末命令，脚本恒以 0 退出。
- 决策：改为 `set -euo pipefail`；显式捕获并传播 `cargo test` 的退出码；编译输出落 `build/tmp/test-lib-build.log`，
  失败时回显日志尾部；`mt.exe` 同时探测 `/c/...` 与 `/mnt/c/...`。
- 理由：门禁必须在失败时失败；编译错误必须可诊断。

### D3 sidecar tier-2 单写者不可变快照（严重）

- 问题：采集线程与 HTTP 线程并发进入 `BuildLocalTier2Payload()`，共享 `_computer`、`_lastValidMap`、`_tier2LastError` 等未加锁可变状态。
- 决策：`GET /api/v1/tier2` 不再现场采集。采集线程把 `Tier2Payload` 作为不可变值发布到受锁保护的快照字段，HTTP 线程只读取该引用后序列化。
  `ReadTier2()` 不再出现在 HTTP 路径上。
- 理由：单写者模型消除跨线程共享可变状态，无需给整棵 LHM 树加锁；代价是 HTTP 最多滞后一轮采集，而采集周期本身即数据新鲜度上限。

### D4 HTTP 白名单改为解析式精确匹配（严重）

- 问题：`url.starts_with(allowed)` 使白名单项加任意后缀/用户信息/端口均通过。
- 决策：白名单改为 `(scheme, host, port)` 三元组，`validate_url` 解析 URL 后逐项全等比较，并拒绝含 userinfo 的 URL。
  函数签名与错误类型保持不变。
- 理由：这是「禁止拼接任意 URL」的唯一执行点，前缀匹配的强度与约束不匹配。当前调用点均为字面量，属恢复约束强度而非修复在利用漏洞。

### D5 消除字节切片与越界索引导致的 panic（严重）

- 问题：`sysinfo.rs` 的 `ImageStateDate` 按字节切分、`network.rs` 的 `inner[0]` 在长度校验前索引、`settings.rs` 的 `guid[..8]`。
- 决策：统一「先证明，再访问」——字符边界安全截断、索引前判空、`get(..8)` 加回退。
- 理由：三处均为输入不合法而非不可恢复状态，应降级返回而非 panic；panic 也不是项目 fast-fail 语义所认可的失败方式。

### D6 MAC 修改失败路径保留回滚信息（严重）

- 问题：`set_network_mac` 写入注册表成功后，禁用/启用网卡失败的错误消息不含原 MAC，与函数头注释承诺不符；失败时网卡可能停在禁用状态。
- 决策：失败消息拼接 `backup` 原值；网卡处于禁用状态时消息必须显式说明该后果。
- 理由：失败路径是用户唯一能获得恢复信息的位置，不能让注释承诺没有实现。

### D7 前端轮询改为 settle-then-schedule（严重）

- 问题：`Dashboard.tsx` 的超时只释放 `inFlight` 而不结束底层 `invoke`，挂起时并发请求线性累积；`NetIfaceContext` 无 in-flight 守卫。
- 决策：传感器轮询改为「上一轮真正 settle 后才排下一次」；网卡轮询补 in-flight 守卫；站点测试补请求代数保护。
- 理由：`withTimeout` 无法取消 Tauri 侧任务，因此不能用「超时即视为本轮结束」作为并发判据。

### D8 发布与提交门禁加固（严重）

- 问题：husky 的 `pre-commit` 缺失导致 lint-staged 从未执行；`package-portable.mjs` 对空 `resources/driver` 放行且不写 zip 内校验和；`.gitignore` 未覆盖嵌套 `bin/obj`；`stage-iperf3` 提示的 `--pin` 不存在。
- 决策：新增并提交 `.husky/pre-commit`；便携包按 `FILES` 逐项校验驱动三件套；修正 `SHA256SUMS` 注释或补写清单；
  `.gitignore` 改为 `sidecar-lhm/**/bin/`、`sidecar-lhm/**/obj/`；实现或删除 `--pin` 提示。
- 理由：交付物完整性必须由内容而非目录存在性判定。

### D9 前端错误处理不吞错、区分空态（一般）

- 问题：Settings/Cleanup/Environment 的 catch 仅在 DEV 记日志，生产静默；`null` 状态被渲染成 `false`，把「读取失败」呈现为「全部关闭」。
- 决策：错误必须给用户可见反馈；`null` 与 `false` 在渲染上必须可区分；「读取失败」与「无数据」用不同空态。
- 理由：静默失败与默认值掩盖是本次审查的主要缺陷类别之一。

### D10 日志 scope 唯一真源（一般）

- 问题：前端 `logs.ts` 的 `MODULE_TO_SCOPE`/`normalizeModule`/`scopeForModule` 零执行，实际解析在 Rust 侧。
- 决策：删除前端那三份实现；`LogScope` 类型与 `scopeForPath` 保留；头注释把唯一真源指向 `log.rs::scope_for_module`。
- 理由：两份真源必然漂移，且其中一份从未被验证。

### D11 契约与字段收窄（一般）

- 问题：`diskSmart.ts` 声明四态而生产者只产两态；`disk.rs` 的 `health_status` 用 `as u8` 截断；`network.rs` 的 TTL 参数被静默丢弃；`hpt.rs` 的 `name` 与同类不一致；`ip_info.rs` 手写 JSON 取值；`tier2_state` 顺序与 `tier2_fields` 相反且无消费者。
- 决策：契约收窄到实际取值域；数值转换改为可控回退；无效入口移除；手写 JSON 解析改用 `serde_json`；顺序相反的死访问器删除。
- 理由：契约描述的取值域必须等于实现能产出的取值域。

### D12 定时器与监听器生命周期（一般）

- 问题：多处 `setTimeout`/`listen` 无卸载清理，`LogsCard` 的监听器存在寄存器泄漏。
- 决策：所有异步注册一律在 cleanup 中释放；监听器采用 `disposed` 标记写法（与 `WindowControls` 对齐）。
- 理由：组件卸载后仍回调 `setState` 与仍接收事件，均属资源泄漏。

### D13 死代码清理（一般）

- 决策：删除全局检索仅命中定义处的符号（Rust 5 个、前端 10 个无导入者组件、sidecar 5 组、scripts 2 处）；
  `driver_uninstall` 与 `tier2_state` 删除；`get_services()` 因有集成测试消费者而保留并补文档说明。
- 判定标准：全局引用搜索无引用。存在动态引用、配置驱动或外部契约调用的一律保留或标待验证。
- **实施期修正（2026-09-24）**：`NetworkManager.SelectBestNetworkHardware` 全局检索仅命中定义，
  一度被判为死代码；但 `CONTRACT-v3.md` §8 明确要求「`NetworkManager` 必须完整移植并在采集循环中
  驱动」——属外部（冻结）契约调用，按上述判定标准**保留并接线**。核查后确认：此前只驱动了
  `ProcessUpdate` 而从未调用 `SelectBestNetworkHardware`，导致 `_cachedNetHw` 恒为 null、
  `isTarget` 恒 false、`ConsumeDelta` 恒返回 (0,0,0)，整条吞吐链路空转——这正是「只写不读」
  在跨语言边界上的表现。同时把采集循环从「只处理第 0 个网络硬件」改为遍历全部。

### D14 重复代码合并（一般）

- 决策：GBK/UTF-8 解码合并到 `proc_util::decode_ps`（`cleanup.rs` 那份策略不同，不合并）；提权检测统一到 `driver_install::is_elevated()`；
  `withTimeout`/`oneLine`/Toast 状态机/Tauri 环境判定/iperf3 终止逻辑各抽一份共用实现。
- 例外：`LiveIndicator` 与 `StatusDot` 合并会改变渲染尺寸，暂不合并。
- 理由：合并后行为必须不变，否则不合并。

### D15 多余代码与依赖清理（建议）

- 决策：删除纯透传包装、恒真分支、恒不命中的查找、永久开启开关、只写不读字段、未使用的开发依赖。

### D16 可观测性与性能（建议）

- 决策：`log.rs` 与 `debug.rs` 的锁改用中毒恢复写法，与全仓既有约定一致；
  日志文件写入改为长驻句柄（对齐 `temp_data.rs` 的 `DiagWriter`）；`tray.rs` 的托盘校验移出主线程。
- **实施期修正（2026-09-24）**：`fix-deliverable-integrity.mjs` 的注释与 `CHANGELOG.md` v2.0.1
  第 5 条均断言「`icacls <目录> /T` 不会改写已存在文件的标签」。本次复测结论**相反**：对只含
  `z.exe`（Low）的目录执行 `icacls <dir> /setintegritylevel "(OI)(CI)Medium" /T` 后，
  `z.exe` 变为 `Medium Mandatory Level:(I)(NW)`。据此更正注释，并说明逐文件循环的真实作用是把
  继承 ACE 换成显式 ACE（并非正确性所必需）。既有 CHANGELOG 条目属历史记录，不改写。
- **未实施**：`tray.rs` 托盘校验移出主线程、`log.rs` 长驻文件句柄。前者涉及启动时序，需实机验证
  托盘登记行为；后者需跨日期切换句柄并与 `temp_data` 的轮转策略协调。两项保留在计划中标记为待办。

## 后果

**正面**：门禁恢复可信；跨线程共享可变状态被消除；用户可见的取消与失败恢复路径成立；契约描述与实现取值域一致。

**负面**：tier-2 HTTP 响应最多滞后采集一轮；部分前端空态需要新增「加载失败」渲染分支；日志句柄需要跨日期切换。

**风险**：D3 涉及 sidecar 主从两条进程的共享状态，必须在修改后实测 tier-1/tier-2 字段既不缺失也不伪造；
D8 的 husky 钩子会改变提交行为，需确认 lint-staged 在真实提交路径上生效。

## 被否决的方案

- **让 `cancel_command` 惰性创建标志**（D1）：可抵御取消先于注册的时序，但迟到取消会留下孤儿条目，且把清理责任从命令转移到注册表。
- **给整棵 LHM 树加统一锁**（D3）：会把采集周期与 HTTP 响应互相阻塞，代价高于快照发布。
- **保留前端 scope 映射并补测试对齐**（D10）：两份真源仍需人工同步，删除零执行的一份成本更低。
- **把白名单校验移到调用点**（D4）：调用点分散在 5 处，约束会随新增调用点失效。
